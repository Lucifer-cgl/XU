# 开放投稿、版权与复用说明

## 一句话原则

XU 不建立账号、投稿后台和版权数据库。想分享课程的人，直接把课程文件、来源与授权声明放进对应目录，通过 GitHub 提交；投稿者为自己提交内容的合法性负责，仓库用文件和 Git 历史完成公开留痕。

这是一个静态、低成本的协作约定，不是自动版权审查系统，也不构成法律意见。

## 为什么不做投稿服务器

传统内容平台通常需要：

- 用户注册和身份系统；
- 投稿表单；
- 数据库；
- 文件上传服务；
- 审核后台；
- 评论和通知；
- 持续运行的服务器；
- 长期安全、备份和运维投入。

这些能力不仅有一次性的开发成本，还有持续的服务器、数据库、安全和人员成本。它们会改变 XU 的产品性质。

XU 选择另一条路线：

1. GitHub 负责身份、提交、差异比较和版本历史；
2. 文件夹负责课程归类；
3. Markdown 负责内容、来源和授权说明；
4. Pull Request 与 Issues 负责交流；
5. Cloudflare 只负责构建和静态分发；
6. 访客浏览器负责阅读、打印与下载。

因此，课程数量增加时，主要增加的是仓库里的内容文件，而不是新的服务端业务。

## 投稿者需要承担什么责任

提交课程即表示投稿者确认：

1. 自己创作了该内容，或者已经取得公开发布与再分发所需的授权；
2. 已如实说明作者、来源、原始链接和改编情况；
3. 没有把付费课程、内部资料、试卷、教材扫描件或其他无权公开的内容伪装成自己的作品；
4. 没有提交个人隐私、账号、密钥或其他敏感信息；
5. 同意仓库保存、公开展示和分发其提交内容；
6. 同意维护者为了格式、安全、排版和目录组织进行必要修改；
7. 发现权利问题时会主动说明并协助更正或移除。

GitHub 账号和提交记录可以说明“是谁在什么时间提交了什么”，但不能自动证明投稿者真的拥有版权。真实性仍由投稿者负责。

## 最低投稿内容

一门新课程至少包含：

```text
content/
└── 分类/
    └── 课程名称/
        ├── 版权与来源.md
        └── 至少一篇课程内容.md
```

可以继续加入：

- `course.json`；
- 完整 HTML；
- 课程图片；
- 课程附件；
- 子目录。

不要求填写在线表单，也不要求写入数据库。

## 版权与来源文件模板

投稿者可以复制下面的内容，保存为课程目录中的 `版权与来源.md`：

```markdown
# 版权与来源

- 课程名称：
- 投稿者：
- GitHub 账号：
- 内容性质：原创 / 授权转载 / 基于公开资料整理
- 原作者：
- 原始来源：
- 原始链接：
- 首次创作或整理日期：
- 本次更新日期：
- 使用的许可证：CC BY-NC-SA 4.0

## 改编说明

说明删减、翻译、重排、AI 辅助整理或其他改动。

## 授权声明

我确认自己有权提交并公开这些文件。除另有明确说明的第三方材料外，
我同意本课程内容按照上述许可证向全球公众开放。
```

这份文件就是最小贡献模板。它只是一个跟随课程保存的静态 Markdown，不需要服务器。

## 默认共享规则

XU 的目标是让课程面向全球免费阅读和学习，而不是建立付费内容平台。

对于新投稿：

- 投稿者没有另外声明时，建议默认使用 **CC BY-NC-SA 4.0**；
- 允许他人阅读、下载、复制、翻译、整理和改编；
- 使用者必须保留署名和来源；
- 不得主要用于商业获利；
- 改编后继续公开传播时，应采用相同或兼容的许可证。

投稿者也可以选择更宽松的许可，例如：

- **CC BY 4.0**：要求署名，允许包括商业用途在内的再利用；
- **CC BY-SA 4.0**：要求署名，改编作品继续采用相同许可；
- **CC0**：在法律允许范围内尽可能放弃权利。

如果投稿者希望禁止商业使用，应明确选择带有 `NC` 条件的许可证。它适合“开放共享、非商业使用”，但不属于某些严格定义下允许任意商业使用的“开源”许可。

许可证一旦用于已经公开的版本，通常不能随意撤销既有使用者已经获得的许可，因此投稿前应认真选择。

Creative Commons 官方说明：

- https://creativecommons.org/share-your-work/use-remix/cc-licenses/
- https://creativecommons.org/cc-license-your-work/

## 上传不等于拥有第三方版权

以下内容不能因为被放进公开仓库就自动变成开放内容：

- 他人的教材扫描件；
- 付费课程讲义；
- 未经授权的题库和答案；
- 带有限制条款的学校内部资料；
- 从网络复制但找不到许可的图片；
- 投稿者所在单位拥有版权的职务作品；
- 仅仅能够下载、但没有再分发许可的资料。

投稿者只能对自己拥有或控制权利的部分选择许可证。引用少量第三方材料时，应保留必要的作者、出处、链接和适用许可，并明确哪些部分不在投稿者授权范围内。

如果无法确认能否公开，最安全的做法是只提供原始来源链接，不把文件复制进仓库。

## 代码与课程内容需要分开授权

平台代码和课程内容不是同一种作品：

- 平台代码适合使用软件许可证；
- 课程笔记、图片和教学材料适合使用 Creative Commons 等内容许可证；
- 第三方附件继续遵守原作者许可。

GitHub 仓库公开可见，不等于任何人已经获得复制、修改和再发布的完整权利。GitHub 官方也说明，没有许可证时默认版权规则仍然适用。

因此，想让其他人放心 Fork、改造和重新部署，仓库未来仍应为平台代码增加明确的软件许可证；每门课程则保留自己的 `版权与来源.md`。

GitHub 许可证说明：

- https://docs.github.com/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository

## 谁负责审核

XU 不承诺建立专业版权审查团队，也不可能自动判断每份材料的真实权利状态。

采用的责任边界是：

- 投稿者负责声明与真实性；
- 合作者可在 Pull Request 中指出问题；
- 维护者可以要求补充来源；
- 信息明显不完整时可以拒绝合并；
- 收到合理权利通知后可以先隐藏或移除争议内容；
- Git 历史保留修改和处理过程。

这是一套“公开声明、社区纠错、必要时下架”的轻量治理方式。

## 统一模板究竟统一什么

XU 不要求所有课程采用完全相同的写作风格，也不需要动态投稿表单。

只统一最少的几项：

1. 文件放进 `content/`；
2. Markdown 只有一个一级标题；
3. 公式、图片和表格符合平台规范；
4. 课程附带 `版权与来源.md`；
5. 构建能够通过；
6. 投稿者通过 GitHub 留下提交记录。

课程正文可以有不同的作者风格、章节长度和组织方式。

## 能否只看数量

纯静态平台很容易统计：

- 课程数量；
- 文档数量；
- 文件数量；
- 文件总体积；
- Markdown 与 HTML 数量；
- 最近一次构建时间。

这些数据可以在构建阶段生成，是一次性功能投入，不需要数据库。

但数量不能代替质量。课程是否正确、有用、完整，仍然需要读者、投稿者和维护者共同判断。

## 哪些能力属于一次性投入

下面这些机制写好后，可以随课程增长自动复用：

- 文件夹扫描；
- 课程目录生成；
- 静态搜索索引；
- Markdown 与公式渲染；
- 三线表；
- 打印样式；
- 原文件下载清单；
- 文件数量和体积分批；
- 来源声明存在性检查；
- 单文件大小检查；
- 内部链接检查；
- 重复文件哈希检查；
- 构建统计。

它们的共同特点是：在提交或构建时运行，结束后释放，不需要常驻服务器。

因此，XU 后续合理的发展方式不是不断增加动态服务，而是逐步增强构建检查和浏览器端能力。

## 为什么课程可以持续增加

新增课程的主要工作是：

1. 创建课程文件夹；
2. 放入原始内容；
3. 补充来源与许可证；
4. 运行构建；
5. 推送 GitHub。

目录、搜索和下载范围都会自动更新。平台代码不需要为每门课程重复开发。

真正持续投入的是内容本身：事实核对、公式检查、课程更新和错误修正。这一部分无法被平台功能完全替代，但可以由不同课程的投稿者分别承担，而不是全部压在平台维护者身上。

## 如何 Fork 成自己的知识库

任何人都可以把 XU 当作一个静态知识库底座：

1. 在 GitHub Fork 仓库；
2. 克隆到自己的电脑；
3. 保留平台代码，删除不需要的示例课程；
4. 把自己的资料放进 `content/`；
5. 修改品牌名称、说明和支持图片；
6. 运行 `npm ci` 与 `npm run build`；
7. 连接自己的 Cloudflare 账号；
8. 部署到自己的域名或 `workers.dev` 地址。

不需要复制数据库，不需要迁移账号，也不需要申请后端服务。

## 如何交给 AI 改造

使用者可以让 AI 先阅读：

1. 根目录 `README.md`；
2. `content/自我介绍/知识库平台_PRD.md`；
3. 本文档；
4. `package.json`；
5. `scripts/build-content.mjs`；
6. `src/` 下的主要文件。

然后告诉 AI：

- 新知识库的名称与主题；
- 需要保留哪些功能；
- 课程资料位于哪里；
- 目标部署平台；
- 是否需要修改颜色、Logo 和首页文案；
- 不允许增加后端与数据库；
- 修改后必须运行完整构建。

AI 可以帮助完成结构调整、内容转换和部署配置，但使用者仍要核对事实、公式、来源、许可证、隐私和最终构建结果。

## Fork 是否需要下载所有课程

Fork 会复制仓库当前受 Git 管理的内容和历史。对于当前规模，这通常不是问题。

如果未来课程显著增多，可以进一步提供：

- 只保留框架和示例的模板分支；
- 不带历史记录的发布压缩包；
- 按学科拆分仓库；
- 使用浅克隆；
- 将超大附件迁移到合适的静态存储。

这仍然不要求业务服务器或数据库。

## 常见疑问

### 没有账号系统，怎么知道是谁投稿

GitHub 提交者、提交记录和 Pull Request 就是身份与修改记录。

### 没有数据库，怎么记录版权

版权和来源写在课程目录的 `版权与来源.md` 中，跟随内容一起版本化。

### 没有评论功能，怎么交流

使用 GitHub Issues、Pull Requests 和 Discussions，不在 XU 内复制一套社区系统。

### 不自动审核，会不会有侵权风险

任何开放投稿都有风险。XU 通过投稿者声明、来源留痕、社区纠错和争议下架降低风险，但不能替代法律审查。

### 上传后是不是任何人都能收费使用

取决于投稿者声明的许可证。默认建议的 CC BY-NC-SA 4.0 不允许商业使用；CC BY 和 CC BY-SA 则允许商业使用。必须看每门课程自己的声明。

### 平台以后是不是要不断维护服务器

不需要业务服务器。持续工作主要是更新内容、依赖和构建规则，Cloudflare 构建结束后不会留下课程处理任务。

### 别人能不能完全做成自己的版本

技术上可以 Fork、换内容、换品牌并重新部署；法律上还需要遵守平台代码和各课程文件的许可证。

## 最终定位

XU 不是一个接管作者权利的内容平台，也不是一个持续收费的托管服务。

它提供的是：

- 一套轻量的静态知识库框架；
- 一套最低限度的投稿与来源约定；
- 一个通过 GitHub 协作的公开过程；
- 一个让课程可以被阅读、下载、修订和再次传播的容器。

平台负责让知识流动，投稿者负责自己提交的内容，读者和社区负责发现问题，Git 负责留下历史。这就是在不建立后端和数据库的前提下，XU 能够长期运行的基本方式。
